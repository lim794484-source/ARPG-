# 面试拷打 —— 从简单到复杂

> 本文档按难度递进组织，覆盖本项目所有核心技术点。每道题包含「问题」和「标准答案」，建议按顺序阅读并在 Unity 中对照验证。

---

## 🟢 Lv1：基础概念（热身题）

### Q1：这个项目的场景架构是怎样的？

**答案：** 三层场景架构。
- `InitialScene` → 启动入口，加载 PersistentScene
- `PersistentScene` → 常驻场景，永不卸载，放所有管理器（SceneChanger、DataManager、UIManager、玩家等）
- `Scene1/Scene2` → 内容场景，通过 Additive 方式加载/卸载

**面试追问：为什么用 Additive 而不是 Single？**
> 因为 PersistentScene 要常驻，Single 模式会卸载所有场景。Additive 允许 PersistentScene + 内容场景同时存在。

---

### Q2：GameSceneSO 是什么？它存了哪些字段？

**答案：** ScriptableObject 资产，每个场景对应一个。字段：
- `ID`（string）：场景唯一标识，存档用
- `sceneReference`（AssetReference）：关联场景文件
- `sceneType`（SceneType 枚举）：Location / Menu / Retry
- `initialPosition`（Vector3）：玩家出生点

**面试追问：sceneType 有什么用？**
> SceneChanger 根据 sceneType 决定是否显示玩家和 UI。Menu 隐藏，Location 显示。

---

### Q3：什么是 ScriptableObject？和 MonoBehaviour 有什么区别？

**答案：**
| 维度 | ScriptableObject | MonoBehaviour |
|------|------------------|---------------|
| 挂载 | 不能挂在 GameObject 上 | 必须挂在 GameObject 上 |
| 实例 | `.asset` 资产文件 | 场景里的对象组件 |
| 生命周期 | 不随场景销毁 | 随场景销毁 |
| 用途 | 存数据/配置 | 运行逻辑 |

---

### Q4：什么是单例模式？本项目怎么实现的？

**答案：** 保证一个类只有一个实例，提供全局访问点。

本项目用泛型抽象基类 `YSingleton<T>`：
```csharp
public abstract class YSingleton<T> : MonoBehaviour where T : MonoBehaviour
{
    protected static T _instance;
    public static T Instance => _instance;

    protected virtual void Awake()
    {
        if (_instance != null && _instance != this)
        {
            Destroy(gameObject);
            return;
        }
        _instance = this as T;
        OnSingletonInitialized();
    }
}
```

子类：`class StatsManager : YSingleton<StatsManager>`

**面试追问：为什么是抽象类？为什么用 `where T : MonoBehaviour`？**
> 抽象类：YSingleton 只是模板，没有具体业务，必须被子类继承才能用。
> 约束：保证 T 是 MonoBehaviour，子类能挂在场景里，`this as T` 才合法。

---

### Q5：抽象类和接口的区别？

**答案：**
| 维度 | 抽象类 (abstract) | 接口 (interface) |
|------|-------------------|------------------|
| 能有字段吗？ | ✅ 能 | ❌ 不能 |
| 能有方法体吗？ | ✅ 能（virtual） | ❌ 不能（C# 8+ 默认方法除外） |
| 继承次数 | 单继承 | 多实现 |
| 适合 | 半成品模板 + 部分实现 | 纯约定/契约 |

本项目：`YSingleton`=抽象类，`ISaveable`=接口，`IDamageable`=接口。

## 🟡 Lv2：事件系统（重点）

### Q6：ScriptableObject 事件和普通 C# 事件有什么区别？

**答案：**

| 维度 | 普通 C# 事件 | ScriptableObject 事件 |
|------|-------------|----------------------|
| 存储 | 脚本里的 event 字段 | 独立的 `.asset` 资产 |
| 耦合度 | 高（必须知道对方类名） | 低（只认资产引用） |
| 跨场景 | ❌ 对象销毁就断 | ✅ 资产不销毁 |
| 可视化 | ❌ 不行 | ✅ Inspector 拖资产 |
| 适合 | 同场景紧耦合 | 跨场景/解耦 |

**核心原理：** SO 事件内部还是 C# 的 `event Action`，但 event 存在资产里，不随场景销毁，所以能跨场景通信。

---

### Q7：为什么 ScriptableObject 事件能跨场景？

**答案：**
- SO 资产是 `.asset` 文件，加载进内存后只要有引用就不卸载
- 场景卸载销毁的是 MonoBehaviour，不是 SO 资产
- 发布者（新场景的对象）和订阅者（常驻管理器）都引用同一个 SO 资产
- 场景切换后，新发布者继续对 SO 说话，老订阅者继续能听到

**对比普通事件：** 普通事件存在发布者对象里，对象销毁 → event 字段销毁 → 连接断了。

---

### Q8：不取消订阅（`-=`）会怎样？

**答案：**
1. **内存泄漏**：发布者（尤其 static）通过委托持有订阅者的强引用，GC 无法回收订阅者
2. **重复执行**：反复 OnEnable 只 `+=` 不 `-=`，委托链越来越长，一次触发多次调用
3. **MissingReferenceException**：已销毁的对象还在执行代码，访问 gameObject/transform 就报错

**规范：** `+=` 写在 OnEnable，`-=` 写在 OnDisable，配对出现。

---

### Q9：本项目有哪些 ScriptableObject 事件？分别用在哪？

**答案：**

| SO 事件 | 用途 |
|---------|------|
| `SceneLoadEventSO` | 场景切换请求（Teleport → SceneChanger） |
| `VoidEventSO` | 无参数通用事件（场景加载完成、玩家攻击完成等） |
| `ToggleCanvasEventSO` | UI 画布开关/焦点 |
| `LootEventSO` | 物品拾取（Loot → InventoryManager） |
| `DataSaveEventSO` | 存档触发（DataManager → SaveSystem） |
| `ShopLoadEventSO` | 商店数据加载 |
| `LoadQuestEventSO` | 任务列表加载 |
| `QuestOptionsEventSO` | 任务选项选择 |
| `OpenSaveLoadPanelEventSO` | 存档/读档面板开关 |
| `InventorySlotsStatsSO` | 商店-背包双向通信 |

## 🟠 Lv3：核心系统

### Q10：场景切换的完整流程是怎样的？

**答案：**
1. 玩家走进传送点 → `Teleport.OnTriggerEnter2D` 调用 `loadEventSO.RaiseLoadRequestEvent(scene, pos, fade)`
2. `SceneLoadEventSO.LoadRequestEvent` 广播
3. 订阅者收到：
   - `SceneChanger`：执行场景异步加载/卸载
   - `DataManager.OnAutoSave`：采集当前场景数据存档
   - `UIManager.OnLoadScene`：重置所有 UI 画布
4. `SceneChanger` 完成加载 → 调用 `sceneLoadedEvent.OnEventRaised()`
5. `VoidEventSO.VoidEvent` 广播 → `DataManager.OnAutoLoad`：把存档数据应用到新场景

**面试追问：为什么 DataManager 要同时订阅加载前和加载后两个事件？**
> 加载前（OnAutoSave）：保存旧场景状态。加载后（OnAutoLoad）：恢复新场景状态。两个时机做不同的事。

---

### Q11：存档系统是怎么设计的？

**答案：** 三层架构。

1. **ISaveable 接口**：需要存档的对象实现 `SaveData(Data)` 和 `LoadData(Data)`，并在 Awake 注册到 DataManager
2. **DataManager**：单例，维护所有 ISaveable 列表。切场景时遍历列表采集数据到 `Data` 对象，然后触发 `DataSaveEventSO`
3. **SaveSystem**：订阅 DataSaveEvent，把 Data 序列化为 JSON 写入磁盘

**关键设计：** 用接口 + 列表，DataManager 不需要知道具体是谁，只管调 SaveData/LoadData。新增可存对象只需实现接口并注册。

---

### Q12：玩家状态机是怎么实现的？

**答案：** 用枚举 + Animator 参数。

- 状态：`Idle`、`Run`、`Attack`、`Shoot`、`Hurt`、`Dead`
- `PlayerState` 枚举记录当前状态
- Animator 用 `isRunning`、`isAttacking`、`isShooting` 三个 bool 控制动画切换
- `canBeInterrupted` 字段控制攻击动画能否被打断

---

### Q13：伤害计算流程是怎样的？

**答案：**
1. 攻击方调用 `DealDamage(target, damage)`
2. 目标实现 `IDamageable.TakeDamage(damage, knockbackDir)`
3. 伤害经过：防御减免 → 暴击判定 → 最终伤害
4. 目标扣血 → 如果血量≤0 → 触发死亡事件

---

## 🔴 Lv4：深入系统

### Q14：A* 寻路算法在本项目怎么用的？

**答案：**
- `AStarNodeManager`：管理格子网络，每个节点存 `gCost`、`hCost`、`fCost`、`parent`
- `AStarPathFinder`：单例，提供 `FindPath(start, end)` 方法
- 敌人 AI 调用寻路获取路径列表，按节点移动

**A* 核心公式：** `f = g + h`
- g = 起点到当前节点的实际代价
- h = 当前节点到终点的预估代价（曼哈顿距离）
- 每次选 f 最小的节点扩展

---

### Q15：UI 管理系统怎么设计的？

**答案：**
- `UIManager`：单例，管理所有画布的开关和焦点
- `ToggleCanvasEventSO`：每个画布对应一个 SO 事件，画布通过订阅事件开关自己
- `CanvasFocusStack`：焦点栈，处理多画布层级和 ESC 关闭逻辑
- `ICanvasManager`：画布接口，统一 `ToggleCanvas` 方法

**设计亮点：** 画布不直接互相引用，都通过 SO 事件通信。

---

### Q16：背包和商店怎么交互的？

**答案：** 用 `InventorySlotsStatsSO` 双向事件。

- `InventoryUpdateRequestEvent`：商店→背包，请求加/减物品
- `InventoryRespondEvent`：背包→商店，返回操作结果
- 购买：ShopManager 调用 `RaiseInventoryUpdateRequest(item, price, 1)` → InventoryManager 加物品扣钱
- 出售：ShopManager 调用 `RaiseInventoryUpdateRequest(item, -price, -1)` → InventoryManager 减物品加钱

---

### Q17：任务系统怎么设计的？

**答案：**
- `QuestSO`：任务数据资产（任务名、描述、目标、奖励）
- `QuestManager`：单例，管理当前任务和完成状态
- `LoadQuestEventSO`：加载任务列表到 UI
- `QuestOptionsEventSO`：任务选项选择
- `VoidEventSO`（openQuestEventSO）：打开任务面板

## ⚫ Lv5：架构与设计（拔高题）

### Q18：这个项目的设计模式有哪些？

**答案：**

| 模式 | 应用 |
|------|------|
| 单例模式 | YSingleton<T>，所有管理器 |
| 观察者模式 | ScriptableObject 事件系统 |
| 接口隔离 | ISaveable、IDamageable、IInteractable、ICanvasManager |
| 数据驱动 | ScriptableObject 存配置（GameSceneSO、ItemSO、QuestSO） |

---

### Q19：这个项目的解耦体现在哪里？

**答案：**
1. **场景解耦**：PersistentScene 常驻，内容场景互不依赖
2. **通信解耦**：SO 事件，发布者和订阅者互不认识
3. **数据解耦**：ScriptableObject 存配置，代码只读不改
4. **存档解耦**：ISaveable 接口，DataManager 不依赖具体类
5. **UI 解耦**：画布通过事件通信，不互相引用

**面试追问：解耦的代价是什么？**
> 调试链路变长（要追踪 SO 事件的发布订阅链），性能略有损耗（多一层中转），但可维护性大幅提升。

---

### Q20：如果让你重构这个项目，你会改什么？

**答案：**（开放题，展示思考深度）

1. **SO 事件统一基类**：抽一个 `EventSOBase<T>` 泛型基类，减少重复代码
2. **存档优化**：当前每次切场景都全量保存，可改为脏标记增量保存
3. **事件日志**：SO 事件缺少运行时追踪，可加调试日志开关
4. **对象池**：Loot、Arrow 等频繁创建销毁的对象用对象池
5. **配置中心化**：把硬编码的数值移到 ScriptableObject

---

### Q21：ScriptableObject 事件有什么缺点？

**答案：**
1. **调试困难**：发布订阅链是运行时动态的，IDE 静态分析找不到
2. **引用易配错**：两个脚本必须拖同一个 SO 资产，拖错了通信不上且不报错
3. **无类型安全**：event 的参数靠约定，编译器不检查发布者和订阅者参数是否匹配
4. **内存占用**：SO 资产常驻内存，数量多时占空间
5. **无法序列化**：SO 事件不能直接参与 Unity 序列化的撤销/重做

---

### Q22：为什么用 ScriptableObject 存数据而不是 JSON/XML？

**答案：**
- SO 直接在 Inspector 可视化编辑，无需手写文本
- SO 支持拖拽引用其他资产（Sprite、AudioClip、Prefab）
- SO 有类型检查，写错字段编译器报错
- SO 随项目打包，运行时直接加载，无需解析
- 适合配置数据，不适合玩家存档（存档用 JSON）

## 🏆 Lv6：终极拷打

### Q23：从玩家走到传送点到新场景加载完成，整个调用链是怎样的？（详述）

**答案：**

```
1. 玩家进入 Trigger
   → Teleport.OnTriggerEnter2D()
   → loadEventSO.RaiseLoadRequestEvent(sceneToLoad, newPosition, true)

2. SceneLoadEventSO 广播 LoadRequestEvent
   三个订阅者同时收到：

   2a. DataManager.OnAutoSave()
       → 遍历 saveables 列表，采集 Loot/Enemy 等状态到 dataToSave
       → 判断场景类型，决定是否写入存档
       → 触发 dataSavedEvent.RaiseDataSaveEvent(SystemSave)
           → SaveSystem.OnSaveEvent() → WriteSave() 写 JSON

   2b. UIManager.OnLoadScene()
       → ResetCanvas() 关闭所有 UI 画布

   2c. SceneChanger.OnLoadRequestEvent()
       → 启动协程，淡出动画
       → 异步卸载旧场景，加载新场景（Additive）
       → 加载完成后设置玩家位置
       → sceneLoadedEvent.OnEventRaised()

3. VoidEventSO（sceneLoadedEvent）广播 VoidEvent
   → DataManager.OnAutoLoad()
       → 遍历 saveables，调用 LoadData(dataToSave)
       → 恢复 Loot 位置、Enemy 状态等

4. 新场景就绪，淡入动画
```

### Q24：DataManager 的 `lastSceneType` 字段解决了什么问题？

**答案：** 解决"菜单→游戏第一次进入不存档"的问题。

- `lastSceneType` 记录上一个场景类型
- 从 Menu 进入 Location 时：重置数据（新游戏），不写系统档
- 从 Location 进入 Location 时：正常存档
- 从 Location 进入 Menu 时：记录当前位置，写系统档

**没有这个判断会怎样？** 每次从菜单进游戏都会把旧存档覆盖，读档功能就废了。

---

### Q25：`IsLoadingSaveRequest` 标志位解决了什么问题？

**答案：** 防止"读档时被自动存档覆盖"。

- 读档流程：SaveSystem.LoadSave() → DataManager.LoadFromData() → loadEventSO.RaiseLoadRequestEvent()
- 触发 LoadRequestEvent → DataManager.OnAutoSave() 会被调用
- 如果没有 `IsLoadingSaveRequest` 判断，OnAutoSave 会把当前（即将卸载）场景的数据采集并覆盖刚读出来的存档
- 加了标志位后，OnAutoSave 检测到是读档请求就直接 return，不污染数据

---

### Q26：InventorySlotsStatsSO 为什么设计成双向事件？

**答案：** 因为商店和背包需要互相确认。

- 单向事件只能"通知"，不能"等结果"
- 购买时：商店请求加物品 → 背包检查有没有空位 → 背包返回结果
- 如果背包没位置，购买失败，商店要知道结果才能决定扣不扣钱
- 所以设计两个事件：`InventoryUpdateRequestEvent`（请求）和 `InventoryRespondEvent`（响应）

---

### Q27：UIManager 的 `[DefaultExecutionOrder(-100)]` 有什么用？

**答案：** 保证 UIManager 的 OnEnable 早于其他脚本执行。

- UIManager 订阅了 `loadEventSO.LoadRequestEvent`
- SceneChanger 也订阅了同一个事件
- UIManager 的 OnLoadScene 要在 SceneChanger 开始卸载场景前关闭 UI
- `-100` 让 UIManager 的回调优先级更高，先执行

---

### Q28：如果两个脚本拖了不同的 SO 事件资产会怎样？怎么排查？

**答案：** 通信不上，且不报错。

**排查方法：**
1. 看发布者的 SO 字段引用的是哪个 `.asset` 文件
2. 看订阅者的 SO 字段引用的是哪个 `.asset` 文件
3. 确认是不是同一个（看文件名和 GUID）
4. 可以加调试日志：在 SO 的 Raise 方法和订阅者回调里都打日志，看哪个没触发

---

### Q29：ScriptableObject 事件和 C# 的 event 关键字底层是一样的吗？

**答案：** 完全一样。

```csharp
// ScriptableObject 里
public event Action<GameSceneSO, Vector3, bool> LoadRequestEvent;

// 本质
private Action<GameSceneSO, Vector3, bool> LoadRequestEvent;
// add { LoadRequestEvent = Delegate.Combine(...); }
// remove { LoadRequestEvent = Delegate.Remove(...); }
```

SO 事件只是把 event 字段放在了 ScriptableObject 类里，利用了 SO 资产的生命周期特性。底层还是多播委托。

---

### Q30：这个项目最大的设计亮点是什么？最大的问题又是什么？

**答案：**

**亮点：** ScriptableObject 事件系统。用资产做通信中转，完美解决了 Unity 跨场景通信的痛点，且完全解耦、可视化配置。

**问题：**
1. SO 事件没有统一基类，每个都要重写一遍 event + Raise 方法
2. 缺少事件追踪机制，调试时要手动找发布订阅链
3. InventorySlotsStatsSO 的双向事件用同步委托实现，如果响应逻辑复杂可能有性能问题
4. 存档每次全量采集，场景对象多时切场景会卡
